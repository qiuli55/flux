# Flux Personal MVP KPI / Acceptance Metrics

> 本文定义 Personal MVP 的量化验收目标。
>
> 原则：先保证任务成功、安全性和状态正确，再优化 Token 成本。Token 指标在 Context Engine 尚未正式实现前，只作为基线指标，不作为当前 MVP 的硬性发布门槛。

## 1. 核心指标

| 指标 | Personal MVP 目标 | 说明 |
|---|---:|---|
| End-to-End 任务完成率 | **≥95%** | 从用户需求开始，到 Proposal → Apply → 测试通过 → Git 状态正确的完整任务比例 |
| 任务首次成功率 | **≥85%** | 不需要人工重新拆解、重新执行或额外重试即可完成的任务比例 |
| MCP 工具调用成功率 | **≥99%** | 工具调用返回预期结果的比例 |
| Proposal 正确率 | **≥95%** | Proposal 与用户需求及 Agent 计划一致，且没有明显无关修改 |
| Apply 成功率 | **≥99%** | 用户批准后正确落盘且没有半应用的比例 |
| Run 状态准确率 | **≥99%** | completed / failed / cancelled / timeout 与实际运行结果一致 |
| Crash Recovery 成功率 | **≥99%** | 可恢复场景不会产生永久 running / 僵尸任务 |
| 移动端核心操作成功率 | **≥99%** | Task / Run / Proposal / Diff / Decision / Cancel 等操作成功率 |
| 移动端核心流程完成率 | **≥95%** | 手机端规定的远程控制流程能够完整完成的比例 |
| 重启数据恢复率 | **100%** | 正常重启后已持久化的数据和状态不丢失、不出现明显错乱 |
| Git 状态准确率 | **100%** | Flux UI 状态与真实 Git 状态一致 |

## 2. 零容忍指标

以下指标不能以 95% 或 99% 作为目标，而应为 **100% 正确 / 0 次事故**：

- Agent 越权访问：**0 次成功越权**
- 密钥 / 凭证泄露：**0 次**
- 未经用户批准的错误 Apply：**0 次**
- 测试失败被报告为成功：**0 次**
- 正常重启导致的数据丢失：**0 次**
- 错误 Git 状态：**0 次**
- 已知禁止操作未被 MCP 权限面拦截：**0 次**

## 3. Token / Context 指标

### 当前 Personal MVP

Context Engine 尚未作为 Personal MVP 的核心能力，因此不以 Token 命中率作为当前发布阻塞条件。

当前只建立基线并记录：

- 单任务输入 Token
- Agent 总输入 Token
- Agent 总输出 Token
- MCP 工具调用 Token 开销（如果可获得）
- 重复上下文 Token
- 任务最终 Token 总量

### 后续 Context Engine

Context Engine 单独验收时，再增加：

| 指标 | 建议目标 |
|---|---:|
| Context / Prompt Cache Hit Rate | **≥90%** 起步，经过真实数据后再调整 |
| 相关上下文召回率 | **≥95%** |
| 重复上下文率 | **≤10%** |
| Context 压缩后任务完成率下降 | **≤2 个百分点** |
| Token 总量降低 | 在不降低任务成功率的前提下测量，不预设硬性节省比例 |

> 注意：不应为了提高 Token 命中率而降低任务完成率。例如从 98% 任务成功率降到 87%，即使 Token 大幅下降，也不属于有效优化。

## 4. 任务完成率的严格定义

一个任务只有完整经过以下链路才算成功：

```text
用户需求
  ↓
任务 / 澄清
  ↓
Agent 执行
  ↓
Proposal
  ↓
用户审核
  ↓
Apply
  ↓
测试通过
  ↓
Git 状态正确
```

以下情况不能算 End-to-End Success：

- 代码“看起来写出来了”，但测试没有通过
- Agent 最终输出成功，但 Flux 状态为错误
- Apply 部分成功但留下半应用状态
- Git 状态与 UI 显示不一致
- 必须人工直接修改代码才能完成
- 必须绕过 Flux 才能完成任务

## 5. 测试样本要求

指标不能只靠少量 Demo 得出结论。

### MCP 工具调用

建议至少积累 **500 次以上**真实或有代表性的 MCP 调用后，再判断工具调用成功率是否达到 99%。

### End-to-End 任务

建议至少执行 **50 个真实开发任务**作为第一轮量化样本；条件允许时增加到 **100 个任务**。

建议覆盖：

- 简单 Bug 修复
- 单文件修改
- 多文件修改
- 新增功能
- 测试补充
- 重构
- Git 操作
- Agent 失败后重试
- Proposal Reject 后重新执行
- 冲突处理
- Cancel / Timeout

### 移动端

建议至少执行 **50 次核心移动端操作**，并至少完成 **20 次完整移动端远程控制流程**。

### 重启恢复

至少执行 **20 次**不同状态下的重启恢复验证，包括：

- 空闲
- 任务运行中
- Proposal pending
- Apply 前
- Apply 后
- 测试运行中
- Git 操作后
- Error / Failed 状态

## 6. 指标记录格式

每轮测试至少记录：

```text
测试总数
成功数
失败数
重试数
人工介入数
异常类型
耗时
Token 输入
Token 输出
Token 总量
```

并计算：

```text
任务完成率 = 成功任务 / 总任务
首次成功率 = 首次完成任务 / 总任务
工具成功率 = 成功调用 / 总调用
Apply 成功率 = 成功 Apply / Apply 总数
移动端成功率 = 成功操作 / 总操作
```

## 7. MVP 发布判定

Personal MVP 进入 Release Candidate 的最低要求：

### 必须达标

- End-to-End 任务完成率 ≥95%
- 任务首次成功率 ≥85%
- MCP 工具调用成功率 ≥99%
- Proposal 正确率 ≥95%
- Apply 成功率 ≥99%
- Run 状态准确率 ≥99%
- Crash Recovery ≥99%
- 移动端核心操作成功率 ≥99%
- 移动端核心流程完成率 ≥95%
- 重启数据恢复率 100%
- Git 状态准确率 100%
- 所有零容忍指标满足 100% 安全要求

### 同时满足

- 至少 50 个真实开发任务样本
- 至少 500 次 MCP 工具调用样本
- 至少 20 次重启恢复样本
- 至少 20 次移动端完整远程控制流程

## 8. 不以 KPI 驱动错误优化

Flux 的 KPI 优先级固定为：

```text
安全性
  ↓
任务成功率
  ↓
状态正确性
  ↓
用户体验
  ↓
Token 成本
  ↓
性能优化
```

不得为了降低 Token、减少模型调用或提高缓存命中率而牺牲任务完成率、代码安全性或用户控制权。

## 9. Personal MVP 最终目标

最终不是追求某一个数字，而是证明：

> **开发者可以连续使用 Flux 完成真实开发工作，并且系统在成功、失败、异常、重启和移动端远程控制场景下都表现出可预测、可解释、可恢复的行为。**
