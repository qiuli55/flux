# Flux Personal MVP — Acceptance Metrics

> 本文档定义 Personal MVP 的量化验收目标。
>
> 原则：**先保证任务正确完成，再优化 Token；先保证安全和状态正确，再追求体验速度。**

## 1. 核心指标

| 指标 | MVP 目标 | 统计口径 |
|---|---:|---|
| End-to-End 任务完成率 | **≥95%** | 从真实需求开始，最终完成 Apply、测试通过并得到正确 Git 结果 |
| 任务首次成功率 | **≥85%** | 不需要人工重新拆任务、重新执行或更换 Agent 即完成 |
| MCP 工具调用成功率 | **≥99%** | 调用返回符合预期协议和语义结果 |
| 已知越权拦截率 | **100%** | 已知禁止操作全部被拒绝 |
| Proposal 正确率 | **≥95%** | Proposal 与需求/执行计划一致，且无明显无关修改 |
| Apply 成功率 | **≥99%** | 用户批准后正确落盘，无半应用、误覆盖或错误状态 |
| 测试门禁正确率 | **100%** | 测试失败不得被报告为成功 |
| Run 状态准确率 | **≥99%** | completed / failed / cancelled / timeout 与真实结果一致 |
| Crash Recovery 成功率 | **≥99%** | 可恢复场景不产生永久 running / 僵尸 Run |
| 移动端核心操作成功率 | **≥99%** | Task、Proposal、Decision、Cancel、Error 等核心操作最终状态正确 |
| 移动端核心流程完成率 | **≥95%** | 手机端能够完成规定的远程控制流程 |
| 重启数据恢复率 | **100%** | 已持久化数据在正常重启后不丢失、不出现明显状态错乱 |
| Git 状态准确率 | **100%** | UI 展示与实际 Git 状态一致 |

## 2. 零容忍指标

以下指标不采用 95% / 99% 之类的容忍线，而是要求测试集中 **0 次发生**：

- Agent 越权访问项目资源
- 读取或泄露密钥、凭证类文件
- 用户未批准的 Proposal 被 Apply
- Apply 错误覆盖用户已有修改
- 测试失败被显示为成功
- 已持久化用户数据因正常重启丢失
- UI 显示成功而后端实际失败
- Git UI 状态与真实状态出现错误确认

## 3. Token / Context 指标

### 3.1 Personal MVP 当前阶段

Token 命中率暂不作为 Personal MVP 的硬性门槛。

原因：当前 Personal MVP 的重点是证明核心 Coding 闭环可靠；Context Engine、持续增量压缩、Prompt Optimizer 等仍属于后续研究方向。

### 3.2 后续 Context Engine 指标

Context Engine 正式进入实现后，再建立独立指标集：

| 指标 | 初始目标 | 说明 |
|---|---:|---|
| Context Cache / Token Hit Rate | **≥90%** | 进入可复用上下文路径的请求比例；后续根据真实数据调整 |
| 相关上下文召回率 | **≥95%** | Agent 所需关键信息仍被保留 |
| 重复上下文率 | **≤10%** | 不必要重复发送的历史上下文占比 |
| Token 消耗降低 | **≥20%** | 与同任务、未启用 Context Engine 的基线比较 |
| 任务完成率变化 | **不得下降** | Context 优化不能以明显降低任务成功率为代价 |

> 注意：Token 命中率不能单独作为优化目标。若 Token 降低但任务完成率明显下降，则优化不合格。

## 4. 任务完成率测试方法

End-to-End Task Success 必须按照完整链路统计：

```text
真实开发需求
  ↓
Solo / IDE
  ↓
Agent
  ↓
Flux MCP
  ↓
Proposal
  ↓
人工审核
  ↓
Apply
  ↓
测试门禁
  ↓
Git 状态
```

只有完整走完并满足预期结果才计为 Success。

### 示例

100 个符合测试范围的真实任务：

- 96 个完整完成
- 2 个需要人工重新执行
- 1 个 Agent 最终失败
- 1 个状态错误

则：

**End-to-End Task Success Rate = 96 / 100 = 96%**

不能因为“代码最后写出来了”就把中途失败的任务计入成功。

## 5. 工具调用成功率

MCP 工具应按单次调用统计：

```text
成功调用数 / 总有效调用数 × 100%
```

需要覆盖：

- context.get
- workspace.read
- workspace.diff
- proposal.create
- 其他 Personal MVP 已实现 MCP 能力

需要分别统计：

1. 正常调用
2. 参数错误
3. 权限拒绝
4. 资源不存在
5. 服务异常
6. 超时

**已知应该拒绝的权限调用不应被计入“失败调用”，而应计入安全拦截成功。**

## 6. Proposal / Apply 指标

### Proposal 正确率 ≥95%

判断标准：

- 修改目标符合用户需求
- 修改范围基本符合执行计划
- 没有明显无关文件
- Proposal 状态正确
- Diff 与 Proposal 描述一致

### Apply 成功率 ≥99%

成功必须同时满足：

- 用户明确批准
- 目标文件正确
- 变更内容正确
- 不覆盖用户已有未批准修改
- Apply 状态正确
- 后续测试能够读取真实落盘结果

## 7. Run / Reliability 指标

重点统计：

- 正常完成
- Agent error
- Provider 无响应
- Cancel
- Timeout
- Flux 重启
- Agent 子进程退出
- 子进程异常残留
- DB 状态与运行时状态不一致

目标：

**Run 状态准确率 ≥99%，Crash Recovery ≥99%。**

任何出现“永久 running 且系统无法解释”的情况，都必须计入失败样本。

## 8. 移动端指标

移动端至少覆盖：

- 登录 / 连接
- Task 查看
- Run 查看
- Proposal 查看
- Diff 查看
- Accept / Reject / Decision
- Cancel
- Error
- 页面刷新后的状态恢复
- 网络短暂中断后的恢复

核心操作成功率目标：**≥99%**。

核心流程完成率目标：**≥95%**。

重点尺寸：**390×844**，同时补充常见 Android 尺寸回归。

## 9. 重启恢复指标

至少执行一组完整测试：

```text
创建项目
 ↓
创建 Task
 ↓
运行 Agent
 ↓
产生 Proposal
 ↓
保存状态
 ↓
关闭 Flux
 ↓
重新启动
 ↓
继续操作
```

以下内容要求恢复率 100%：

- Project
- Task
- Task Messages
- Agent Registry
- Proposal
- Apply 状态
- Git 信息
- 可恢复的 Run 状态

## 10. 建议的最小测试样本

为了让百分比具有基本统计意义，Personal MVP 验收建议至少积累：

| 测试项 | 最小样本 |
|---|---:|
| End-to-End 真实任务 | **≥50**，正式发布前建议 ≥100 |
| MCP 工具调用 | **≥500** |
| Proposal | **≥50** |
| Apply | **≥50** |
| Cancel | **≥20** |
| Timeout | **≥10** |
| Crash Recovery | **≥20** |
| 重启恢复 | **≥20** |
| 移动端核心操作 | **≥100** |
| 越权 / 安全测试 | **所有已知攻击矩阵全部通过** |

样本不足时可以记录当前结果，但不要把结果当成稳定的长期指标。

## 11. MVP Release Gate

Personal MVP 进入 Release Candidate 的最低门槛：

```text
任务完成率             ≥95%
首次成功率             ≥85%
MCP 调用成功率         ≥99%
Proposal 正确率        ≥95%
Apply 成功率           ≥99%
Run 状态准确率         ≥99%
Crash Recovery         ≥99%
移动端核心操作         ≥99%
移动端核心流程         ≥95%
重启数据恢复           100%
Git 状态准确           100%
已知越权拦截           100%
安全零容忍项           0 次失败
```

并且：

> **任何 P0 / P1 安全或数据一致性问题未关闭，都不得因为平均指标达标而发布。**

## 12. 指标优先级

当指标之间发生冲突时，优先级固定为：

```text
安全
 ↓
数据正确性
 ↓
任务完成率
 ↓
Run / 状态可靠性
 ↓
用户体验
 ↓
Token 成本
 ↓
性能优化
```

因此：

> **不能为了节省 Token 而牺牲任务完成率，也不能为了提高速度而牺牲变更安全。**

## 13. Personal MVP 的最终判断

当上述指标达到 Release Gate，并且开发者能够在真实项目中连续使用 Flux 完成工作时，Personal MVP 才视为真正收口。

此后再根据真实使用数据决定是否进入下一阶段，而不是根据预先设想继续增加功能。
