# Flux UI 用户级测试方案

> 目的：在现有功能测试、MCP/Agent 闭环测试基础上，对 Flux 做一次**真实用户视角的 UI / UX 测试**。
>
> 本测试不是单纯检查“按钮能不能点”，而是让测试 Agent 按照真实开发者目标完成任务，观察用户能否理解页面、找到入口、做出正确决策、完成工作，并记录所有阻塞、误导、认知负担和视觉层级问题。

## 1. 测试目标

重点验证：

1. 首次进入 Flux 后，用户能否理解 Flux 是什么、从哪里开始。
2. 用户能否快速进入项目并开始工作。
3. IDE Workspace 是否真正以代码工作区为中心，而不是被无关面板占据。
4. 不常用页面能否被隐藏/关闭，并能通过明确入口重新打开。
5. Solo 是否与 IDE Workspace 形成清晰区别，并能完成单 Agent / 编排式任务。
6. Agent、Task、Context、MCP、Proposal、Diff、Apply 等概念是否容易理解。
7. 用户能否理解什么时候需要人工审核，以及审核前后发生了什么。
8. Agent 遇到问题时，“使用默认方案 / 我来决定”的行为是否直观。
9. 用户能否发现任务状态、Agent 状态、失败、取消、等待和完成状态。
10. DSH 与 Codex 的使用流程在 UI 层是否保持一致，而不会让用户感知到不必要的实现差异。
11. 错误、权限拒绝、冲突、超时、取消等异常是否能让用户知道发生了什么以及下一步该做什么。
12. 桌面端与手机端的核心控制流程是否可理解、可操作。

参考原则：可用性测试应以真实任务为核心，而不是让用户单纯浏览页面；任务应尽量接近真实用户目标，并避免在任务描述中提前告诉用户应该点击哪里。citeturn0search0turn0search6

# 2. 测试方式

## 2.1 Agent 的角色

执行测试的 Agent 不应扮演“开发 Flux 的程序员”，而应尽量扮演：

> 一个第一次或第二次使用 Flux 的开发者。

测试 Agent 可以查看源码和页面实现，但**不能因为看过代码而假设用户知道页面结构**。

如果 Agent 能直接修改代码，则测试阶段禁止修改产品代码；只能：

- 使用产品
- 记录问题
- 截图/录屏（若环境支持）
- 输出测试报告

不得为了让测试通过而修改 UI。

## 2.2 测试环境

至少准备：

- 桌面端完整 Flux
- 一个真实/测试项目
- DSH Agent
- Codex Agent
- 正常网络
- 可制造异常的测试场景
- 手机端或移动尺寸页面

建议 DSH 与 Codex 各执行一次核心任务，以验证 UI 是否真正 Agent-agnostic。

---

# 3. 测试原则

## 3.1 不提前告诉 Agent 点击路径

错误方式：

> 点击左侧 Workspace，然后点击 New Task，再点击 Solo。

正确方式：

> 你刚接手一个项目，现在需要让一个 AI Agent 帮你实现登录功能，请使用 Flux 完成这个任务。

这样才能测试真正的 discoverability。

## 3.2 不要用“看起来不错”作为通过标准

每项测试都应该有：

- 用户目标
- 起始状态
- 成功标准
- 观察点
- 实际路径
- 阻塞点
- 用户是否犹豫
- 用户是否误解

## 3.3 记录“第一次反应”

尤其关注：

- 第一个点击是什么
- 第一个输入是什么
- 用户第一次找不到什么
- 用户第一次误点什么
- 用户第一次问“这个是什么意思”是什么

这些通常比测试结束后的主观评价更有价值。

---

# 4. 测试等级

建议分为四层：

### L0：视觉与基础交互

验证布局、响应式、按钮、弹窗、滚动、焦点、加载状态等。

### L1：信息架构与可发现性

验证用户能否理解页面和找到功能。

### L2：真实开发任务

让用户从需求开始，经过 Agent、Proposal、审核、Apply、测试、Git 完成闭环。

### L3：异常与恢复

验证失败、冲突、取消、权限拒绝、Agent 卡住等情况下用户是否能继续工作。

---

# 5. L0：视觉与基础交互测试

## UI-001：首次打开

### 用户任务

> 第一次打开 Flux，请先自己判断这个产品是做什么的，并找到开始开发的位置。

### 观察

- 首屏是否能理解产品定位
- 是否存在明显主入口
- 是否需要阅读说明才能开始
- 是否出现过多信息
- 用户是否知道“项目”与“Agent”的关系

### 通过标准

用户不需要阅读源码或测试人员解释，即可找到合理的开始路径。

---

## UI-002：桌面端主布局

### 用户任务

> 打开一个项目，准备开始正常写代码。

### 观察

- IDE 是否占据主要工作区域
- 代码区是否为视觉中心
- 是否存在不必要的固定面板
- 左右栏是否抢占主要空间
- Agent / Task / Context 信息是否在需要时出现

### 特别检查

Flux 当前设计目标是：

> 工作时 IDE 页面占大部分；不必要的页面可以关闭，并通过一个明确按钮重新打开。

测试必须验证这个目标是否真的成立。

---

## UI-003：面板关闭与重新打开

### 用户任务

> 你现在只想专心修改代码，请把不需要的辅助面板关掉；过一会儿又需要查看任务状态，请把它重新打开。

### 观察

- 用户能否发现关闭入口
- 关闭后页面是否真正释放空间
- 重新打开入口是否容易发现
- 用户是否担心“关闭后功能消失”
- 面板状态是否符合预期

---

## UI-004：窗口尺寸变化

测试至少：

- 1920×1080
- 1440×900
- 1280×800
- 1024×768

观察：

- IDE 是否仍为核心区域
- 是否出现横向滚动
- 面板是否挤压代码
- 按钮是否被隐藏
- 弹窗是否超出屏幕

---

# 6. L1：导航与信息架构

## UI-101：页面认知

让 Agent 不查看路由代码，仅根据 UI 判断：

- IDE Workspace 是什么
- Solo 是什么
- Agent 是什么
- Task 是什么
- Context 是什么
- Proposal / Diff / Apply 分别意味着什么

记录任何需要解释才能理解的概念。

---

## UI-102：页面之间切换

### 用户任务

> 你正在开发一个项目，现在需要在代码工作区、Agent 工作流和项目状态之间切换。

观察：

- 用户是否知道去哪里
- 导航层级是否合理
- 返回是否符合预期
- 是否出现“页面套页面”
- 是否需要频繁跳转

---

## UI-103：隐藏页面的可发现性

对于非核心页面：

- Agent Detail
- Task Board
- Cost Dashboard
- Skill Marketplace
- Connector Marketplace
- Settings

验证：

> 页面默认不抢占 IDE 空间时，用户是否仍然能在需要的时候找到它们。

重点检查“隐藏”和“不可发现”之间的区别。

---

# 7. L2：真实 IDE 用户任务

## UI-201：创建/打开项目

### 场景

> 你刚拿到一个已有项目，需要在 Flux 中开始工作。

测试：

1. 找到项目
2. 打开项目
3. 查看项目结构
4. 找到关键文件
5. 开始一个开发任务

记录完整路径和所有犹豫点。

---

## UI-202：直接给 Agent 一个任务

### 场景

> 给 Agent 一个真实需求，例如：
>
> “给这个项目增加一个登录页面，支持邮箱和密码登录，并补充基本错误提示。”

不要告诉 Agent 使用哪个按钮。

测试：

- 找到 Agent
- 选择 Agent
- 输入任务
- 开始执行
- 查看进度
- 查看 Agent 当前状态

分别使用 DSH 与 Codex 执行一次。

---

## UI-203：需求追问流程

### 场景

故意给出一个信息不完整的需求：

> “给我做一个用户管理功能。”

观察 Flux 是否能够让 Agent 先澄清需求，而不是直接开始工作。

检查：

- 用户是否知道 Agent 在等待自己回答
- 问题是否清晰
- 多轮问题是否容易回答
- 已经回答的问题是否被重复询问
- 最终需求是否有明确确认点

---

## UI-204：人工审核点

### 场景

执行一个包含需要人工决定的修改任务。

观察：

- 哪些操作需要审核是否明显
- Proposal、Diff、Apply 的关系是否容易理解
- 用户能否看到“Agent 想做什么”
- 用户能否看到具体文件修改
- Approve / Reject / 修改意见是否清晰
- Reject 后用户知道下一步是什么

---

## UI-205：Diff 阅读

### 用户任务

> Agent 提交一个包含多个文件修改的 Proposal，请判断是否应该应用。

观察：

- 用户能否找到 Diff
- 是否知道哪些是新增/删除/修改
- 多文件修改是否容易理解
- Diff 与 Proposal 的关系是否清晰
- 用户是否担心 Apply 会直接覆盖代码

---

## UI-206：Apply 后验证

### 用户任务

> 审核并应用修改，然后确认任务是否真的完成。

观察：

- Apply 状态是否明确
- 测试结果在哪里
- Git 状态在哪里
- 用户能否判断 Agent 是否真正完成
- `finish_reason=error` 等异常是否会被错误显示为完成

---

# 8. Solo 页面测试

Solo 不测试 IDE 面板堆叠，而测试它作为独立 AI 工作流控制台的体验。

## UI-301：Solo 单 Agent 任务

### 用户任务

> 在 Solo 页面直接给一个 Agent 下发任务，并观察任务完成过程。

检查：

- 是否一眼知道这里可以给 Agent 发任务
- Agent 选择是否清晰
- 任务输入是否足够突出
- 执行状态是否清晰
- 结果是否容易查看

---

## UI-302：小模型任务编排

### 用户任务

> 给 Flux 一个复杂需求，让内置小模型帮助拆分任务并安排 Agent。

例如：

> “给这个项目增加登录、用户资料页和权限控制。”

观察：

- 用户是否知道 Flux 正在进行编排
- 任务拆分是否容易理解
- Agent 分配是否透明
- 用户是否知道哪些任务并行、哪些依赖前置任务

---

## UI-303：Agent 追问

测试不完整需求：

> “做一个带支付功能的 App。”

观察：

- Flux 是否主动进入需求澄清
- 问题是否按优先级出现
- 用户是否能知道还缺哪些信息
- 完成澄清后是否明确进入执行阶段

---

## UI-304：执行中的二次决策

### 场景

第一轮需求澄清完成，Agent 已开始工作。

随后让 Agent 遇到一个需要选择的问题。

验证 UI 是否清楚表达：

```text
使用默认方案

vs

我来决定
```

其中：

- **使用默认方案**：Agent 不把问题打给用户，自动采用默认方案继续执行。
- **我来决定**：Agent 将具体方案提交给用户，由用户选择后继续。

重点不是按钮有没有，而是用户是否能准确理解两个选项的后果。

---

# 9. Agent 状态与任务状态

## UI-401：Running

观察：

- 用户是否知道 Agent 正在工作
- 是否知道正在执行哪个任务
- 是否能判断是否正常等待

## UI-402：Waiting for User

观察：

- 是否明显区别于 Running
- 用户是否知道自己需要做什么

## UI-403：Completed

观察：

- 是否能看到实际结果
- 是否能看到修改内容
- 是否能看到测试结果

## UI-404：Failed

制造真实失败。

检查：

- 错误是否明显
- 错误原因是否能理解
- 是否能重试
- 是否能取消/结束
- 是否能继续任务

特别检查：

> `finish_reason=error` 不得显示为“Agent 执行完成”。

## UI-405：Cancelled

取消一个正在执行的 Agent：

- UI 是否立即显示 CANCELLING / Cancelled 的正确状态
- 用户是否知道取消是否已经真正完成
- 是否可以安全重新运行

---

# 10. 异常场景 UI 测试

## UI-501：权限拒绝

例如 Agent 尝试读取 `.env`。

用户应该能看到：

- 操作被拒绝
- 原因
- 是否需要用户处理

不能只显示一个模糊的“执行失败”。

## UI-502：Workspace 冲突

制造文件已经发生变化的情况。

检查：

- 冲突是否明显
- 是否保护原文件
- 用户是否知道应该怎么处理

## UI-503：Agent 超时

制造 Provider 长时间无响应。

检查：

- 是否显示等待/异常
- 是否最终进入 Timeout
- 用户是否能取消
- 用户是否知道是否可以重新运行

## UI-504：Apply 失败

制造 Apply 中途失败或恢复场景。

检查：

- 用户是否知道 Apply 是否完成
- 是否能看到恢复/回滚入口
- 是否会误以为代码已经完整修改

---

# 11. Git 用户体验

## UI-601：查看修改

用户完成 Agent 任务后：

> 我想知道 Flux 改了什么。

观察用户能否自然找到：

- Diff
- Changed Files
- Git 状态
- Proposal

## UI-602：提交

> 我确认修改没有问题，现在我要提交代码。

观察：

- Commit 入口是否容易找到
- 用户是否理解提交范围
- 提交成功后状态是否明确

## UI-603：回滚

> 我发现刚才的修改有问题，需要恢复。

观察：

- 用户是否能找到 Rollback
- 是否知道 Rollback 会影响什么
- 是否存在误操作风险

---

# 12. 手机端测试

手机端不是简单把桌面端缩小，而应测试“远程控制开发工作流”的核心任务。

## UI-701：查看任务

用户在手机上：

> 查看当前 Agent 正在做什么。

检查：

- 当前任务
- Agent 状态
- 进度
- 最近事件

## UI-702：处理 Agent 问题

> Agent 在执行过程中请求用户决定。

用户应能够在手机上：

1. 看到问题
2. 理解方案
3. 选择默认方案或自己决定
4. 让任务继续

## UI-703：审核 Proposal

用户在手机上查看一个 Proposal：

- 能否理解修改目的
- 能否查看关键 Diff
- 能否批准/拒绝

## UI-704：异常处理

手机端收到：

- Failed
- Timeout
- Permission Denied
- Waiting for User

检查是否能理解状态并采取合理操作。

---

# 13. 可访问性与视觉一致性

不要求本轮达到完整无障碍认证，但至少检查：

- 文本与背景有足够对比度
- 主要按钮容易辨认
- 错误不能只用颜色表达
- 键盘焦点清晰
- Hover / Active / Disabled 状态明显
- Loading 状态明显
- 图标含义不会完全依赖猜测
- 相同操作在不同页面使用相同术语

---

# 15. 严重程度定义

## P0

核心任务完全无法完成，或者存在严重误导/数据风险。

## P1

核心任务可以完成，但普通用户很容易卡住，需要人工解释或明显绕路。

## P2

体验明显不合理，但用户经过尝试可以完成。

## P3

视觉、文案、细节或一致性问题，不影响核心任务。

---

# 16. 最终测试报告必须回答的问题

测试 Agent 最后不要只输出“通过/失败”，而必须回答：

### A. 首次使用

> 一个没有看源码、没有产品培训的开发者，能否独立开始使用 Flux？

### B. IDE

> Flux 是否真的把 IDE 作为主要工作空间？

### C. Solo

> Solo 是否真正成为独立的 AI 工作流控制台，而不是另一个 IDE 页面？

### D. Agent

> 用户是否理解 Agent 在做什么、什么时候需要自己决定？

### E. Proposal

> 用户是否能理解 Agent 想修改什么，并安全地进行人工审核？

### F. 异常

> Agent 失败、超时、取消、权限拒绝时，用户是否知道发生了什么以及下一步怎么办？

### G. DSH / Codex

> 换成另一个 Agent 后，用户是否仍然能用同样的方式完成任务？

### H. Mobile

> 用户是否能通过手机完成真正有价值的远程控制，而不是只能查看状态？

---

# 17. 最终输出物

测试完成后，要求生成：

```text
UI_TEST_REPORT.md
```

报告至少包含：

1. 测试环境
2. 测试版本 / commit
3. 测试设备与尺寸
4. 完成的测试项
5. 未执行项及原因
6. P0/P1/P2/P3 问题列表
7. 每个问题的复现步骤
8. 截图/录屏引用
9. 核心任务完成率
10. 首次使用阻塞点
11. 信息架构问题
12. UI 视觉层级问题
13. DSH 与 Codex UI 对等性
14. Mobile UX 问题
15. 建议修复顺序

不要根据主观审美给 Flux 打一个总分，也不要简单输出“UI 很好/不好”。应以具体任务、证据和复现步骤描述问题。

---

# 18. 推荐执行顺序

```text
L0 视觉 / 基础交互
        ↓
L1 导航 / 信息架构
        ↓
L2 真实开发任务
        ↓
DSH 核心闭环
        ↓
Codex 核心闭环
        ↓
Solo
        ↓
异常 / 恢复
        ↓
Git
        ↓
Mobile
        ↓
```
