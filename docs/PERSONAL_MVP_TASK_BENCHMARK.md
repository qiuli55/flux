# Flux Personal MVP Task Benchmark

> 用真实开发任务验证 Personal MVP，而不是只验证单个功能。
>
> 第一版基准：50 个任务，覆盖基础、中等、复杂、异常和真实开发场景。

## 1. 任务分布

| 类型 | 数量 | 目的 |
|---|---:|---|
| 基础任务 | 10 | 验证基本闭环 |
| 中等任务 | 15 | 验证工程开发能力 |
| 复杂任务 | 10 | 验证跨模块开发能力 |
| 异常任务 | 10 | 验证可靠性与状态一致性 |
| 真实开发任务 | 5 | 验证真实使用价值 |
| **合计** | **50** | |

## 2. 基础任务（10）

1. 给 README 增加安装和启动说明。
2. 新增简单健康检查 API。
3. 给现有 API 增加参数校验。
4. 新增一个简单数据表及 CRUD。
5. 给现有函数补充单元测试。
6. 修复明确的 TypeScript 类型错误。
7. 修复简单 Python 异常处理问题。
8. 给现有页面增加 Loading 状态。
9. 给按钮增加错误提示。
10. 修改一个现有组件样式并通过测试。

## 3. 中等任务（15）

11. 新增一个完整的小功能，从 API 到前端。
12. 修改 API 返回结构并同步前端。
13. 增加分页功能。
14. 增加搜索功能。
15. 增加筛选功能。
16. 给现有功能增加权限判断。
17. 修改数据库 Schema 并完成迁移。
18. 增加一个新的 MCP Tool。
19. 修改一个现有 MCP Tool 的参数。
20. 增加一个新的 Agent 配置。
21. 修复一个真实的异步状态 Bug。
22. 修复一个前端竞态问题。
23. 增加一个异常恢复逻辑。
24. 修改一个已有任务的生命周期。
25. 给已有功能补完整测试。

## 4. 复杂任务（10）

26. 新增一个完整的小模块。
27. 对现有模块进行重构，同时保持测试通过。
28. 同时修改数据库、Backend 和 Frontend。
29. 同时修改 MCP、Agent 和 Backend。
30. 增加一个完整的 Task 状态流转。
31. 增加一个新的 Proposal 类型。
32. 修改涉及多个文件的核心逻辑。
33. 修复一个跨前后端 Bug。
34. 给已有功能增加权限、UI 和测试。
35. 完成一个需要 5～10 个文件修改的真实需求。

## 5. 异常任务（10）

36. Agent 执行过程中 Cancel。
37. Agent 执行过程中模拟 Provider 超时。
38. Proposal 产生后用户 Reject。
39. Proposal 与用户当前修改产生 Conflict。
40. Apply 过程中制造失败。
41. 测试阶段故意让测试失败。
42. Agent 子进程异常退出。
43. Flux 后端重启后恢复任务。
44. Run 长时间无响应。
45. Git 工作区存在未提交用户修改时执行 Agent。

异常任务不以“最终代码是否完成”为唯一标准，重点检查：错误识别、状态准确性、权限边界、数据完整性、是否错误 Apply、是否误报成功。

## 6. 真实开发任务（5）

46. 使用 Flux 给 Flux 自己增加一个真实的小功能。
47. 使用 Flux 修复 Flux 自己发现的一个 Bug。
48. 使用 Flux 对 Flux 某个模块进行一次真实重构。
49. 使用 Flux 完成一个独立小项目中的真实功能。
50. 只给出真实需求，不提供实现步骤，让 Flux 自己完成完整开发闭环。

## 8. KPI 计算

### 端到端任务完成率

```text
完整完成任务数 / 可执行任务总数
```

目标：**≥95%**。

### 首次成功率

```text
无需重新描述、人工重新拆解或重新启动执行而完成的任务数 / 可执行任务总数
```

目标：**≥85%**。

### MCP 工具调用成功率

```text
正常返回预期结果的调用数 / 工具调用总数
```

目标：**≥99%**。

对于预期的 `permission_denied`，如果权限判断本身正确，不应作为工具实现失败。

### Proposal 正确率

目标：**≥95%**。

### Apply 成功率

目标：**≥99%**。

### Run 状态准确率

目标：**≥99%**。

### Crash Recovery

目标：**≥99%**。

### 移动端

核心操作成功率：**≥99%**。

核心流程完成率：**≥95%**。

## 9. 安全红线

以下结果必须为 0：

- 越权访问成功
- 密钥 / 凭证泄露
- 未经批准的错误 Apply
- 测试失败却报告成功
- 正常重启导致数据丢失
- UI 与实际 Git 状态错误

## 10. 样本要求

50 个任务是第一版完整 Benchmark，不建议只跑其中最简单的任务后宣称 MVP 达标。

在正式判断 KPI 前，至少完成全部 50 个任务，并保留每个任务的原始记录。

如果样本不足，应标记：

```text
SAMPLE_INSUFFICIENT
```

而不是 PASS。

## 11. 测试原则

1. 基础任务可以使用明确需求。
2. 中等和复杂任务应逐步减少实现提示。
3. 异常任务应主动制造故障。
4. 真实开发任务尽量使用真实项目需求。
5. 最终任务不得预先告诉 Agent 应该修改哪些文件。
6. 不为了得到高完成率而修改任务定义。
7. 记录失败，不隐藏失败。
8. Token 数据只作为观测指标，当前 Personal MVP 不以 Token 优化阻塞发布。
