# Flux Mobile Controller 稳定性测试方案

> 目标：针对当前 Personal MVP 移动端控制器，在不新增业务功能的前提下，建立一套可重复的验收测试。重点验证配置、任务、Terminal、SSE 实时流、停止控制、生命周期和异常恢复。

## 1. 验收原则

- 先保证正确性，再关注性能。
- 所有失败都必须表现为可恢复的 UI 错误，而不是闪退、卡死或静默失败。
- 手机关闭页面不应意外停止服务端 Agent/命令；用户明确点击 Stop/Force Stop 才允许停止。
- SSE 断线后必须能够恢复，并尽量补齐断线期间产生的事件。
- 不以“功能能跑一次”为通过标准，而以连续、重复、异常场景下仍然稳定为通过标准。

## 2. P0：发布阻断项

### P0-1 配置保存

测试：
1. 输入正确 Base URL + Token，保存。
2. 输入错误 Token，保存并测试连接。
3. 输入非法 URL。
4. 清空 Token 后保存。
5. 快速连续点击保存 5 次。
6. 保存过程中切后台，再回来。

通过标准：
- 正确配置成功进入任务页。
- 错误配置显示明确错误，不闪退。
- 非法输入不会触发网络请求或异常退出。
- 连续点击不会产生重复导航、重复请求或崩溃。
- 配置读取失败时有重试入口。

目标：保存成功率 >= 99/100；配置异常闪退次数 = 0。

### P0-2 启动恢复

测试：
- 已保存完整配置启动 20 次。
- 配置存在但 DataStore 读取异常时启动。
- 启动过程中立即切后台/恢复。

通过标准：20 次启动全部进入正确页面；异常配置进入可恢复错误页。

目标：启动成功率 >= 99%；Crash = 0。

### P0-3 Terminal 基本闭环

测试：
1. 创建 Terminal session。
2. 执行 `echo hello`。
3. 执行一个持续输出命令。
4. Stop。
5. Force Stop。
6. 再创建新 session。

通过标准：命令输出、exit code、session 状态均正确；Stop 与 Force Stop 都能结束对应进程；新 session 不受旧 session 影响。

目标：任务/命令完成率 >= 99/100。

## 3. P1：核心可靠性

### P1-1 SSE 断线恢复

测试：
- Terminal 输出过程中主动断网 5~10 秒，再恢复。
- App 切后台 30 秒后恢复。
- 服务端重启后重新打开 Terminal。

通过标准：
- UI 显示 connecting/error 状态，而不是假装 live。
- 网络恢复后自动重连。
- 重连后能够从 lastSeenSeq 附近补读历史事件。
- 不重复显示大量相同事件。

目标：断线恢复成功率 >= 95/100；关键事件丢失率 <= 1%。

### P1-2 HTTP 与 SSE 竞态

测试：连续执行 20 次短命令，例如 `echo 1` 到 `echo 20`。

检查：command.started、output、command.finished 的顺序和 exit code。

目标：20/20 命令完成；事件顺序错误 0 次；重复事件 0 次。

### P1-3 长时间 Terminal

测试：连续运行 30 分钟，产生至少 3000 行输出。

通过标准：
- UI 不明显卡顿。
- 内存不会随事件数量无限增长。
- 旧 transcript 按上限淘汰。
- 重连不会重复堆积历史。

目标：30 分钟无崩溃；客户端事件列表保持有限大小。

### P1-4 Stop 边界

测试：
- 空闲 session 点击 Stop。
- 命令执行中点击 Stop。
- Stop 后立即点击 Force Stop。
- 已停止 session 再次点击 Stop。
- 网络断开时点击 Stop。

通过标准：按钮状态与 session 状态一致；已停止 session 不重复发送停止请求；停止失败可见且可恢复。

目标：停止操作错误率 < 1%；误停止其他 session = 0。

## 4. P2：体验稳定性

### P2-1 Task Detail

测试：创建/打开包含 100、500、1000 条消息的任务。

检查：
- 自动滚动到真正最后一条消息。
- 页面进入/退出不闪退。
- 快速打开多个任务不会串数据。

目标：1000 条消息仍可正常浏览；错误滚动/崩溃 = 0。

### P2-2 页面生命周期

测试矩阵：
- Task → 后台 → 前台。
- Terminal → 后台 → 前台。
- Terminal 页面退出 → 重新进入。
- 手机旋转/配置变化（若当前 Activity 配置允许）。

通过标准：ViewModel 状态不丢失；不会重复建立无限 SSE；不会因为离开页面误停止服务端任务。

## 5. P3：性能基线

记录以下数据即可，不要求当前版本为了数字而过度优化：

| 指标 | Personal MVP 目标 |
|---|---:|
| 配置保存成功率 | >= 99% |
| 启动成功率 | >= 99% |
| Terminal 命令完成率 | >= 99% |
| SSE 自动恢复成功率 | >= 95% |
| 关键事件丢失率 | <= 1% |
| 重复事件率 | <= 0.5% |
| Crash | 0 |
| ANR | 0 |
| Stop 误操作 | 0 |
| 30 分钟 Terminal 崩溃 | 0 |

## 6. 推荐实际验收顺序

1. 配置保存 20 次。
2. App 冷启动 20 次。
3. Terminal 创建/执行/Stop/Force Stop 各 20 次。
4. 连续短命令 20 次。
5. SSE 断网恢复 10 次。
6. 后台恢复 10 次。
7. 30 分钟长输出。
8. Task Detail 大消息量测试。
9. 最后再做 APK Release 构建。

## 7. 最终 Personal MVP 判定

满足以下条件即可进入个人版验收，不要求继续为了“完善”而无限加功能：

- P0 全部通过。
- P1 全部通过。
- P2 无阻断性问题。
- P3 指标达到目标或已经确认瓶颈不影响正常个人使用。
- Crash/ANR 为 0。
- Token 保存、Terminal 控制、SSE 恢复三个核心链路可以重复使用。

达到上述标准后，下一阶段重点应从“继续加功能”切换到：桌面端打包、正式个人版体验验收、安装包发布和后续项目学习，而不是继续无止境扩展移动端功能。
